# OFFLINE-MAP-REAL-003B validation

## Scope and provenance

This run validates the OFFLINE-MAP-002 archive and rebuild path on the recovered
team recording `flight_20260822_190116_ros2`. It does not change localization
parameters, add a global pose graph, or publish a production loop constraint.

- Source zip: 5,641,830,400-byte ROS 2 bag archive, SHA256
  `30d93315264d7e6576ce01c496df52d8a566937a826dcd9d7073147b57329c63`.
- Source database SHA256:
  `96a8075145817013c5ff6ff1008081ff4e1de0227fa9edc8b5a3b90cc9cd9a56`.
- Duration: 65.580 s.
- LiDAR: 656 `sensor_msgs/msg/PointCloud2` messages at approximately 10 Hz,
  13,117,728 points total.
- IMU: 13,118 messages at approximately 200 Hz.
- The source has no odometry, so `/Odometry` was generated by the existing
  `fast_lio_real_mid360.yaml` configuration after transport normalization.

All generated bags, scans, PCDs, logs, and manifests remain outside Git. The
source bag was opened read-only and its hashes were unchanged.

## PointCloud2 MID360 adaptation

The observed point layout is 26 bytes: `x/y/z/intensity` float32, `tag/line`
uint8, and absolute `timestamp` float64. The adapter:

- rounds and clamps finite `intensity` into Livox `reflectivity`;
- preserves finite XYZ including zero, point order, `line`, and `tag`;
- copies IMU serialized bytes unchanged;
- keeps the original header and uses it as CustomMsg `timebase`;
- computes `offset_time` as
  `round(float64(point_timestamp) - float64(header_stamp_ns))`;
- rejects negative/non-representable offsets instead of clamping or restamping.

The same-float64-domain subtraction is required because one timestamp ULP at
this Unix epoch is 256 ns. The initially attempted
`round(timestamp) - integer_header` contract produced artificial offsets in
`[-127, 127]` ns and was rejected. The corrected conversion produced 656/656
valid scans with offsets from 0 to 101,751,296 ns, no non-finite XYZ rejection,
and exactly 13,117,728 output points.

Normalization wrote a 255.8 MiB derived bag in 496.95 s with 82.7 MiB maximum
RSS. Most wall time is sequentially traversing the 5.25 GiB source database,
which also contains camera payloads; the implementation remains streaming.

## FAST-LIO pose generation and archive

The normalized CustomMsg and unchanged IMU were replayed through the existing
real MID360 configuration (`lidar_type: 1`). The run produced 651 odometry
messages. The prior PointCloud2 probe emitted 645 missing-reflectivity warnings;
the normalized run emitted none. Three pre-initialization scans were skipped by
FAST-LIO, after which IMU initialization and KD-tree mapping proceeded normally.

The materializer accepted 650/656 LiDAR scans and wrote 12,997,632 points to
immutable per-scan NPZ files. Six pre-initialization scans were rejected because
their nearest pose was 100.3--600.5 ms away; no tolerance was widened. It also
preserved all 651 trajectory samples in `trajectory_original.csv`. Runtime was
88.82 s with 71.2 MiB maximum RSS. The scan-to-body calibration is the existing
FAST-LIO configuration value: translation `[-0.011, -0.02329, 0.04412]` m and
identity rotation. The bag has no independent static TF for this calibration,
so hardware-calibration provenance remains a limitation.

## Four-map comparison

The original-pose rebuild used a 0.20 m evidence voxel and a maximum 250 ms pose
bracket. Per-point deskew applies
`T_map_body(t_i) * T_body_lidar * p_i` using only bracketing trajectory states,
linear translation interpolation, and shortest-path quaternion SLERP.

| Product | Points / voxels | Result |
|---|---:|---|
| Raw scan-pose map | 12,997,632 points | scan-level pose baseline |
| Deskewed map | 12,977,664 points | 649 scans; one first-scan `missing_left_state` rejection |
| Voxelized map | 116,249 voxels | 99.104% reduction from deskewed points |
| Cleaned map | 99,798 voxels | 14.152% of evidence voxels removed |

Cleanup removed 16,178 low-support voxels, 173 spatially isolated voxels, and
100 voxels in small weak components. Stable multi-frame ground and wall
retention were both 100%. Retention over all plane candidates was 88.31% for
ground and 89.59% for walls; the difference is deliberately discarded
single-observation fringe rather than loss of stable structure.

The occupied-voxel ghosting proxy decreased from 663,195 in the scan-pose map
to 450,495 after per-point deskew, a 32.072% reduction. Per-point correction was
14.4 mm at P50 and 66.7 mm at P95. A rebuild took 83.20 s with 423.71 MiB peak
RSS. A second original-pose rebuild produced byte-identical PCDs:

## Single-session loop smoke

Keyframe export selected 17 candidates and exported 16; the first was rejected
for the same causal `missing_left_state` condition. The smoke test reused PR18's
ESF database and point-to-plane registration implementation.

- Retrieved candidates: 50; geometrically verified: 23.
- Best pair: query keyframe 14 / scan 542 to candidate keyframe 0 / scan 141.
- Temporal separation: 40.099 s; ESF distance: 0.018192.
- Registration: converged, 8,837 correspondences, 98.53% overlap.
- Reciprocal ratio: 53.17%; point-to-plane inlier RMSE: 84.27 mm.
- Plane-error P90: 99.04 mm; effective rank: 6; condition number: 66.05.
- Runtime: 3.98 s; maximum RSS: 58.2 MiB.

This proves that the recording contains a repeat-region candidate that passes
the current geometric gates. It is not evidence of a completed loop closure:
no loop constraint was inserted, no global pose graph was optimized, and no
corrected trajectory was produced.

## Outcome and next boundary

The real recording is suitable to freeze the PointCloud2 adapter, causal
per-point deskew, immutable archive, deterministic original-pose rebuild, and
single-session retrieval/verification smoke. It is suitable as the first input
to an independent global pose graph, subject to retaining the calibration
provenance limitation and validating more/larger real sessions.

The next stage should keep the fixed-lag localization backend unchanged and add
an offline global-pose-graph module with explicit keyframe/edge schemas,
robustly validated loop constraints, corrected pose revisions, and a full map
rebuild from the immutable scan archive. Acceptance must compare corrected and
original trajectories/maps and must not use evaluator truth online.

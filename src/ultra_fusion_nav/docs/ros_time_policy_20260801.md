# ROS 仿真时钟策略

## 目的

定位、融合、可靠性调度、任务状态机和精度评价统一使用 ROS 2 `/clock` 对应的仿真时间。Gazebo 的时间膨胀系数只改变仿真时间相对于现实时间的推进速度，不应改变同一传感器数据和同一航迹的定位结论。

## 时间分层

| 用途 | 时间源 | 规则 |
| --- | --- | --- |
| 因子时间、预积分、观测新鲜度 | 消息 `header.stamp` / ROS 时钟 | 不使用回调到达时刻替代采样时刻 |
| Scheduler 状态、悬停和航点进度 | `node.get_clock()` | 时间回退时清空候选、pending 队列或中止当前任务 |
| ATE/RPE、轨迹配对、采集时长 | 消息源时间戳 / ROS 时钟 | 报告 `sim_duration_s`，横轴是仿真秒 |
| 线程等待、服务确认、TCP 重连、启动超时 | `time.monotonic()` | 仅用于现实执行看门狗，不进入定位或健康评分 |
| 回调、优化、边缘化和 CPU | `perf_counter()` / 进程 CPU 时间 | 报告为 `*_wall_ms`、`cpu_utilization_percent` |

## Gazebo 边界

`gazebo_clock_bridge` 订阅 `/world/<world>/clock`，发布 ROS `/clock`。所有仿真算法启动入口默认传递 `use_sim_time:=true`。桥接器不会把消息到达时刻伪装成采样时刻；如果 FCU 或外部设备时间域与仿真时钟不一致，应在边界显式映射并同时保留原始时间用于诊断。

算法入口拒绝零时间戳和明显不同时间域的观测，不再自动用 callback now 补写。可靠性分数和 Scheduler 新鲜度依据消息头时间；仿真 MTF-01P 链路直接使用输入图像/光流的仿真采样时刻。航点插值、悬停和 setpoint 发布频率按仿真秒推进。

节点启动时不得把尚未生效的 ROS 时间 `0` 当作实验起点。采集器、动态目标和监测器从首个正值 ROS 时间开始计时；时钟回退时，评价任务明确失败，纯监测窗口则清空后重新建立，避免把两个时间段拼接成一条轨迹。

## 评价口径

报告至少同时包含：

- `sim_duration_s`：用于定位精度和算法行为的仿真时长；
- `wall_duration_s`、`observed_rtf`：用于描述执行速度；
- `solve_wall_ms`、`callback_wall_ms`、CPU 占用率：用于算力评估。

性能监测额外报告 WSL 系统总 CPU 利用率的 median/P95/max，口径为全部逻辑核总容量的 `0..100%`，并标记为系统级指标；它用于判断 Gazebo 与算法的总体算力压力，不冒充单个 ROS 节点的 CPU 占用。

低 RTF 只能说明实时计算能力不足，不能单独判定定位精度失败。若 `/clock` 停止，仿真时长、因子新鲜度和安全状态均应停止推进；现实墙钟看门狗仍可终止卡死的进程。

## 当前验收顺序

1. 检查 `/clock` 存在、非零且单调推进。
2. 对同一 bag 在不同 RTF 下回放，比较 ATE/RPE、因子接受和状态切换。
3. 分离定位精度与现实计算负载报告。
4. 在时钟一致性通过后，再处理后端发散保护、故障归因和原生点面模型。
